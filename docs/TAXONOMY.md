# Таксономия требований InspectorX

Как требования раскладываются по категориям. Документ описывает действующую
модель данных и подтверждает её отраслевыми аналогами. Написан 12.07.2026 по
товарной оси; актуализирован 29.07.2026 — тег «род требования» внедрён, добавлена
ось услуг.

## Короткий вывод

- **Данные уже размечены правильно.** Каждое из 203 требований по сигаретам (срез
  переноса из v1) несёт три измерения: `operation`, `transport_type`,
  `lifecycle_stage`. Проблема
  «плоского списка» была **чисто фронтовой** — старый экран группировал только по
  этапу и игнорировал операцию и транспорт. Перекатегоризация данных **не нужна**.
- **Модель совпадает с эталонами.** Иерархия `операция → транспорт → этап → требование`
  — это буквально информационная архитектура национального портала Узбекистана
  **uztradeinfo.uz** (цель/товар → процедура(операция × транспорт) → шаг → документы),
  а сам набор операций — это таможенные процедуры по Киотской конвенции ВТамО.
- **Одно осмысленное расширение — уже внедрено (12.07.2026).** Тег **«род требования»**
  (SPS / техрегламент / маркировка / лицензия / налоги / валюта / таможня /
  происхождение) — как на EU Access2Markets и WTO ePing. Он отвечает на вопрос
  «какого рода это требование». Показывается цветным бейджем, данные не переписывает.
- **Появилась восьмая операция — услуги.** Модуль услуг (12.07.2026) добавил
  `operation = service` со своей формулой: режим допуска × 6 этапов жизни бизнеса.

## Три измерения (что уже есть в БД)

Таблица `requirements`, поля:

1. **`operation`** (`operation_domain`) — что делает бизнес. 8 значений, три группы:
   - Требования к товару на рынке РУз: `product`, `realization`.
   - Внешнеэкономические процедуры: `import`, `export`, `transit`, `re_import`, `re_export`.
   - Услуги: `service` — добавлено 12.07.2026 модулем услуг, см. раздел «Ось услуг».
2. **`transport_type`** (`avto` / `train` / `avia`) — только внутри трансграничных
   процедур; у `product`/`realization` пусто (это корректно).
3. **`lifecycle_stage_id`** → справочник `lifecycle_stages` (упорядоченный чек-лист:
   «Регистрация импортного контракта», «Таможенное оформление», «Маркировка» и т.д.).
   Внутри `realization` под-этапы: ввод в оборот · ценообразование · опт · розница.

Итого требование к товару = `операция × (транспорт?) × этап`. Это и рисует интерфейс
товара: верхние вкладки = операции; внутри процедуры = переключатель транспорта;
внутри — чек-лист по этапам; в каждом этапе — строки требований. У услуг формула
своя (см. «Ось услуг»).

## Ось услуг (`operation = service`)

Восьмое значение `operation_domain` добавила миграция модуля услуг
`supabase/migrations/20260712100000_services_module.sql`. На проде 58 требований
с `operation = service` из 345 всего (55 published + 3 draft).

Формула здесь другая — **режим допуска × 6 этапов жизни бизнеса**:

- **режим допуска** — enum `admission_mode` (`license` / `permit` / `notification` /
  `free`), поле `services.admission_mode`; на проде заполнен у 2 услуг из 11
  (аптека ОКЭД 47.73 — `license`, кафе ОКЭД 56.10 — `free`), у остальных 9 — null;
- **этапы** — вместо транспорта 6 сервисных этапов `svc-01-start` … `svc-06-closure`
  (sort_order 101–106): «Старт и допуск», «Помещение и запуск», «Текущая работа»,
  «Проверки», «Изменения и продление», «Прекращение»;
- **адресат** — `party_role` = `service_provider`;
- **применимость** — по ОКЭД: scope `oked_code` / `oked_prefix` (код ОКЭД содержит
  точку, формат кода расширен той же миграцией). Фактически на проде используются
  `oked_code` (83 строки) и `all_services` (29); `oked_prefix` — 0 строк.

Источник модели — `docs/SERVICES_PASSPORT_PROPOSAL.md` (утверждено фаундером 12.07.2026).

## Универсальность (для будущих товаров)

Структура на ~90% продукт-агностична: этапы — это процессы-глаголы (регистрация
контракта, разрешительные документы, сертификация, таможенное оформление,
маркировка), одинаковые для сигарет, молока, лекарств. Товаро-специфичен только
**набор конкретных требований внутри этапа** (ветеринарное свидетельство для
молока, регистрация в реестре ЛС для лекарств) — а это контент, не структура.
Ничего «сигаретного» в осях нет.

## Тег «род требования» (NTM) — внедрён 12.07.2026

Свёртка 16 глав классификации UNCTAD NTM в 8 понятных категорий-бейджей:

| тег | что это | NTM |
|-----|---------|-----|
| `sps` | санитария / ветеринария / фитосанитария | A |
| `tbt` | техрегламент, сертификация, качество | B |
| `marking` | маркировка и упаковка | A3/B9 |
| `licensing` | лицензии, квоты, разрешения, запреты | C/E/P1 |
| `fiscal` | пошлины, акцизы, налоги, цены | F + тариф |
| `currency` | валютные / финансовые требования | G |
| `customs` | таможенные формальности и документы | C |
| `origin` | происхождение, СТ-1 | O |

**Статус: сделано.** Миграция `supabase/migrations/20260712010000_requirement_category.sql`
завела enum `requirement_category` из тех же 8 значений и nullable-колонку
`requirements.requirement_category`; бэкофилл — эвристика по названию этапа плюс
заголовок требования. На фронте чип строит `categoryChipOf` (`src/data/taxonomy.ts`):
приоритет у значения из БД, для не-услуг фолбэк на ту же эвристику `categoryOf`;
рендер — `src/pages/c/CRequirementList.tsx`, колонка выбирается в `src/data/real.ts`.

На проде (29.07.2026) тег заполнен у 255 из 345 требований, пуст у 90
(realization 55, service 20, по 3 в import/export/transit/re_export/re_import).
Распределение заполненных: customs 63, tbt 57, marking 30, fiscal 28, sps 26,
currency 22, licensing 21, origin 8. У 20 услуг без тега чип не показывается
сознательно (эвристика по заголовку для услуг врёт), остальные 70 закрывает
фолбэк-эвристика. Решения фаундера больше не требуется; открыто одно — уточнение
тега контент-редактором для 90 строк.

Из того же ряда уже сделано: пометка «разовое / постоянное» — колонка
`requirements.nature` (enum `requirement_nature`, миграция модуля услуг),
рисуется чипом рядом с бейджем категории.

Остаётся на потом (display-only, без миграции): признак «обязательно / если
применимо», актор-исполнитель, страна происхождения/назначения.
