# Vision MVP — handoff ночной сессии Claude Code (30.07.2026)

> **Кому:** автономная ночная сессия Claude Code.
> **Что строим:** новый отдельный проект `inspector-vision` — сервис проверки фото
> продукта/упаковки на соответствие требованиям оформления (фича InspectorX).
> **Контекст экосистемы:** InspectorX — compliance-платформа для Узбекистана
> (см. `docs/TARGET_FORMAT.md` в repo inspector-x-final). Vision — первая «активная
> проверка»: клиент шлёт фото коробки/этикетки → система показывает, ЧТО не так и ГДЕ.

## Цель ночи (одним предложением)

Работающий локальный пайплайн: фото → детекция элементов оформления → OCR →
проверка чек-листа → **аннотированное фото с обведёнными проблемами** + JSON-вердикт,
с демо-страницей для ручного тыканья утром.

## Жёсткие рамки

- **Никакого облака ночью.** Railway/Docker — только Dockerfile написать, не деплоить.
- **VLM разрешён только для разметки датасета** (авторазметка), НЕ как рантайм-модель

- **Скоуп только фото.** Проверка документов клиента, ТН ВЭД-логика, интеграция
  с InspectorX-базой — вне скоупа ночи. Чек-лист — зашитый (см. ниже).

## Пилотный чек-лист (зашить в конфиг, YAML)

Проверяем фото экспортной упаковки на наличие и читаемость:

1. этикетка/маркировочная зона присутствует;
2. штрих-код присутствует и декодируется (pyzbar/zxing);
3. текстовая маркировка присутствует и читаема OCR-ом (латиница + кириллица;
   узбекский латиницей и русский);
4. знаки соответствия/сертификации (если различимы) — детекция «знак присутствует»;
5. общее качество фото (размытость/освещённость) — если фото негодное, честно
   сказать «переснимите», а не выдавать ложный вердикт.

Вердикт по каждому пункту: `pass / fail / unreadable / retake_photo` + координаты
(bbox) для отрисовки на фото.

## План ночи (фазы с гейтами; каждая фаза коммитится отдельно)

### Фаза 0 — рисёрч и решения (≤1 ч)
Выбрать и зафиксировать в `docs/DECISIONS.md`: модель детекции (дефолт — Ultralytics
YOLO nano/small, обучение на MPS/CPU), OCR (дефолт — PaddleOCR или EasyOCR,
проверить кириллицу+латиницу), zero-shot fallback (YOLO-World или GroundingDINO).
Не залипать: дефолты годные, менять только по явной причине.

### Фаза 1 — скелет пайплайна на zero-shot (гейт: работает end-to-end)
FastAPI: `POST /check` (фото → JSON-вердикт + путь к аннотированному фото) +
CLI `python -m vision.check photo.jpg`. Внутри: zero-shot детектор + OCR + барcode +
rule-engine по чек-листу + отрисовка bbox с подписями проблем (красный fail,
зелёный pass, жёлтый unreadable). **Это страховка: даже если обучение ночью
провалится, пайплайн уже рабочий.**

### Фаза 2 — датасет (гейт: ≥300 размеченных изображений)
Источники: открытые датасеты (Roboflow Universe: packaging/label/barcode;
Open Images: box/carton/label) — скачать, привести к нашим классам
(label_zone, barcode, text_block, cert_mark). Дыры в разметке закрыть
VLM-авторазметкой с ручной валидацией выборки (проверить 30 случайных, записать
процент ошибок разметки в отчёт). НЕ скрейпить Google Images.

### Фаза 3 — обучение (гейт: своя модель ≥ zero-shot по mAP на нашем val-сплите)
Дообучить YOLO nano/small на собранном датасете. Train/val 80/20. Записать метрики
(mAP50, mAP50-95, per-class) в `docs/TRAINING_REPORT.md` вместе с выводом:
сколько изображений на класс дало какое качество — владелец хочет понять,
сколько данных нужно собирать дальше. Если своя модель хуже zero-shot —
пайплайн остаётся на zero-shot, это НЕ провал ночи, зафиксировать причины.

### Фаза 4 — демо и «красиво» (гейт: можно тыкаться в браузере)
Минимальная веб-страница (может быть однофайловый HTML при FastAPI): drag&drop фото →
аннотированный результат + чек-лист с зелёными/красными пунктами по-русски,
человеческие формулировки («Штрих-код не читается — переснимите ближе»),
в духе InspectorX: клиент видит ГДЕ проблема и ЧТО делать.

### Фаза 5 — верификация и упаковка
Тесты: 5+ юнит (rule-engine, storage) + e2e-скрипт на 10 тестовых фото с ожидаемыми
вердиктами. Dockerfile (не деплоить). README: установка, запуск, как дообучать.
Итоговый отчёт `docs/NIGHT_REPORT.md`: что сделано/не сделано, метрики,
качество разметки, известные слабости, что владельцу посмотреть утром первым делом.

## Правила автономной работы

- Застрял на фазе >1.5 ч — записать блокер в NIGHT_REPORT, перейти дальше
  (фазы 4–5 важнее идеального обучения).
- Ничего не удалять в других репо, работать только в inspector-vision.
- Каждый гейт — коммит + строка в NIGHT_REPORT.
- Все строки, видимые пользователю, — по-русски.

## Что НЕ делать (записано, чтобы не расползтись)

- Не интегрировать с InspectorX/Supabase/Bridge — только абстракция storage.
- Не деплоить на Railway.
- Не строить админку, авторизацию, биллинг.
- Не пытаться покрыть все категории товаров — один пилотный чек-лист.
