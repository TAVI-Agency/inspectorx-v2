## Что вышло иначе (сверка с фактом 29.07.2026)

- **Админки в приложении нет** (п. 3 плана): в `src/App.tsx` только лендинг, кокпит C
  и auth-страницы. Ревью черновиков идёт из терминала: `importer review list|show`
  (`importer/cli.py`) и скрипты `research-loop/` (requeue_review, pass2_autoclear);
  хуки под админку в `src/data/hooks.ts` написаны, но ни один компонент их не вызывает.
- **Конвейер не на Railway и не Bridge** (п. 4 плана): Bridge не чинили, Railway не заводили
  (в репозитории нет ни railway-конфига, ни Dockerfile/Procfile). Конвейер написан заново
  как локальный Python-пакет `importer/` и запускается с машины владельца.
- **Мониторинг изменений законодательства не построен** («неделя 2-3»): на проде
  `change_events`, `requirement_change_impacts`, `user_notifications` — по 0 строк,
  лента изменений в кабинете работает на мок-фикстурах (`src/data/index.ts`).
  В Telegram уходят только заявки с сайта — триггеры на трёх таблицах заявок
  (`supabase/migrations/20260727120000_lead_notifications.sql`, 27.07.2026).
- **Услуги как отдельный тип паспорта — сделаны** (были в разделе «Дальше»):
  на проде 11 услуг, в том числе аптека (ОКЭД 47.73) и кафе (ОКЭД 56.10).
- Из открытых вопросов ниже п. 1 (цена тарифа) **не закрыт**: цена лежит в `src/config.ts`
  и не утверждена.

## Главное решение

**InspectorX — основной продукт.** Строим его С НУЛЯ, сразу качественно, минимальным
объёмом. Старый код InspectorX (Lovable) НЕ полируем и НЕ развиваем — из него забираем
только контент (перенос скриптом) и проверенные UX-находки.

## Что мы строим (5 частей, порядок стройки)

1. **БД (новый Supabase-проект)** — единая таблица требований со связями:
   к кодам ТН ВЭД/ИКПУ, к пунктам актов JurisBase, статусы draft→review→published,
   контент на 3 языках, confidence. Контракт полей — TARGET_FORMAT.md §4.
   ЭТО ПЕРВЫЙ ШАГ — всё остальное зависит от схемы.
2. **Витрина (Vercel)** — поиск (товары+услуги) → страница товара (паспорт → список
   уровня 0 → карточка 3 уровней) → пейволл → кабинет (мои товары, лента изменений).
   ТЗ витрины = TARGET_FORMAT.md целиком.
3. **Админка** — очередь ревью черновиков от AI, правка, публикация. Ревьюер — дядя.
4. **Конвейер (Railway) = Bridge** — используем по назначению: JurisBase → LLM-обработка →
   черновики в очередь ревью. Чиним только 3 критичных бага (потеря карточек, дубли,
   доставка мимо confidence-гейтинга) + переписываем CardMapper на новую схему.
   Остальные баги Bridge (health check, Temporal, стабы) — НЕ трогаем.
5. **JurisBase** — в первые недели НЕ трогаем (Bridge уже умеет поллинг из него).
   Неделя 2-3: стабильные ID пунктов актов (для точных уведомлений «изменилось ваше
   требование») — единственная запланированная правка.

- **Сейчас (день 1):** схема БД в Claude Code (по TARGET_FORMAT §4) → миграции →

- **Неделя 2-3:** уведомления (JurisBase diff → затронутые карточки → лента/Telegram),
  правка JurisBase (ID пунктов), Click-оплата.
- **Дальше:** 3 языка (переводчик JurisBase уже есть), услуги как отдельный тип паспорта,
  AI-чат по карточкам.

## Ключевые продуктовые решения (детали в TARGET_FORMAT.md)

- Продукт = «чек-лист соответствия бизнеса», не «справочник законов».
- MVP: единый вид для всех (без персонализации по ролям — v2).
- Товары + услуги с первого дня (услуги — отдельный тип паспорта, спроектировать).
- Поиск кода: гибрид (автоподсказки + AI-уточнение при неоднозначности + дерево).
- Пейволл: вход и первый уровень бесплатно, детали карточек и уведомления — по подписке.
- Ни одна карточка не публикуется без человеческого ревью; три метки доверия
  (AI-черновик / проверено юристом / официальный ответ).
- GR-ответы госорганов обезличенно обогащают FAQ — накапливающееся преимущество.
- Пустые разделы скрываются; «нет по закону» ≠ «ещё не наполнили».
