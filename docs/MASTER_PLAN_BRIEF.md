# MASTER_PLAN_BRIEF — бриф для написания единого мастер-плана

> Дата: 02.08.2026. Собран в Cowork-сессии с Абдурахмоном.
> Назначение: исходник для грил-сессии в Claude Code, по итогам которой пишутся два плана:
> **План №1** — единый гигантский (одна большая фаза, полная ориентация, Claude Code работает по нему без остановок).
> **План №2** — точечный, по отдельным вещам (пишется позже отдельно).
> Этот документ — не план. Это зафиксированные решения + материал.

## 1. Цель продукта (куда целимся)

InspectorX — мультистрановая compliance-платформа: «чек-лист соответствия бизнеса».

- **Страны:** старт **Узбекистан + Казахстан вместе**, затем **ОАЭ** (контент через английский; арабский не нужен). Языки контента: ru/uz/en — контракт уже в схеме.
- **Объекты:** **товары (HS6) и услуги (UNSPSC) запускаются вместе**, ничего не оставляем сзади. Национальные слои кодов per-страна: ИКПУ/ТН ВЭД у УЗ, свои у KZ/UAE (см. ADR-0004).
- **Судебные кейсы (SudX):** пока только УЗ. Другие страны — не добавлять.
- **Фото-чек (контур B из Miro):** отдельная фаза, другой репозиторий. В мастер-план НЕ входит.

## 2. Стратегия исполнения: две параллельные ветки

Работаем параллельно, соединяем в конце:

1. **Ветка InspectorX** (этот репо): схема БД с jurisdiction, Build-конвейер (§5), витрина (мультистрановость, сравнение), календарь, подписка.
2. **Ветка LegalX** (отдельные сессии): починка `search_norms` (сейчас сделан некачественно), webhook изменений, большие апдейты, данные Казахстана.

**Между ветками — зафиксированные контракты** (ADR-0005 + расширения из §6). Контракты пишем/фиксируем сразу, в начале; физическое соединение веток — в конце, когда обе готовы. До соединения InspectorX может строиться против моков контрактов.

Приоритет внутри параллели: первая задача LegalX — `search_norms`, иначе Build-конвейер строится против сломанного поиска и golden set ничего не покажет. Ветки «встречаются» на golden set (~20 требований, размеченных руками).

## 3. Мультистрановость — принятая модель (вариант «страна как переключатель»)

- Товар один, глобальный (HS6/UNSPSC — мировые коды). На карточке товара — **табы стран** (UZ / KZ / UAE), каждый таб показывает требования этой страны.
- **Кнопка «Сравнить»** рядом с табами → матрица: строки = типы требований (сертификация, маркировка, санитарка, лицензия, техрег…), колонки = страны, ячейка = есть / нет / статус. Сравнение работает **на уровне продукта** — так видно, что в одной стране айтема вообще нет.
- Сравнение возможно только через **общую таксономию типов требований** → карта Cartographer становится **двухуровневой**: (1) общая мировая карта категорий регуляторных айтемов, (2) per-страна карта конкретных айтемов. Первые 2–3 задачи конвейера по новой стране определяют, как страна «смотрит» на требования (структура, статусы, специфика).
- Схема: `jurisdiction` в requirements (и по цепочке в scope/contents/details); запуск страны = прогон того же конвейера с новым jurisdiction.
- В существующей терминологии/UI встречаются УЗ-специфичные слова («кабул» и т.п.) — при мультистрановости нужна корректировка общего формата показа данных. Общий формат показа определяется в начале Build.

## 4. Подписка и календарь-фича

- Пейволл как сейчас: тизер бесплатно (`requirement_contents`), мясо под подпиской (`requirement_details`), граница — RLS на сервере.
- **Новая фича (внутри подписки): календарь дедлайнов.** Когда у требования наступает дата жизненного цикла (вступление в силу, конец переходного периода, утрата силы) — событие ставится юзеру в **Google Calendar** + приходит **нотификация**. Только по товарам/услугам, на которые юзер подписан (добавил в кабинет). Это расширение задачи «Cron переходов статуса» из Miro (контур C, строка 31): cron уже вычисляет переходы — календарь и нотификации вешаются на те же события. Нужен OAuth Google у юзера.

## 5. Build-конвейер (контур A) — источник: docs/miro-agent-flow.csv + ADR-0003

Полная таблица из Miro лежит в `docs/miro-agent-flow.csv` (51 строка: контуры A · Build, B · Runtime-фото, C · Monitoring, D · Инфра). Мастер-план должен разложить контур A целиком, контур C (webhook, impact-маппер, cron переходов, discovery, нотификации), контур D (golden set, трейсинг+стоимость). Контур B — исключить (отдельная фаза).

Скелет конвейера (для ориентации, детали в CSV):

1. Оркестратор Build — код + статусы в БД, LLM-менеджер только на исключениях, Абдурахмон — последний уровень (needs-attention).
2. Cartographer: карта регуляторных айтемов группы (теперь двухуровневая: мир → страна) → **апрув карты Абдурахмоном** (единственный обязательный человек в контуре).
3. Question writer → Retriever (`search_norms`) → Verifier (Норма) — независимый: другая модель/промпт, не видит рассуждений Retriever. Различать «нормы нет в стране» vs «поиск не нашёл».
4. Summarizer + Verifier; Classifier'ы: категория, Rule-maker (JSON-правила — критичная точка), Scope-резолвер (коды), Lifecycle-экстрактор (даты).
5. Санкции: Retriever → Verifier → структуризатор {статья, штраф, мера}. Судебные кейсы (SudX, только УЗ): топ-5, снапшот линков, саммари.
6. Samples judge → Template hunter (веб-поиск шаблонов) → Verifier. In-house lawyer: инструкция «что делать». Translator uz + Verifier.
7. Дедупликация (эмбеддинги + Classifier на спорных) → Assembler (карточка по TARGET_FORMAT §4) → загрузка в БД (draft) → Coverage checker → публикация (все Verifier pass → published; фейл ×N → needs-attention).
8. Статус действия — **вычисляемое поле** из дат (upcoming/in_force/transitional/expiring/repealed), не хранится текстом.

Тиры моделей и триггеры (manual/step/event/cron) — в CSV, колонки «Тир модели» и «Триггер».

## 6. Контракты между ветками (зафиксировать в начале)

Основа — ADR-0005, расширения из этой сессии:

- `search_norms(query, …, jurisdiction)` — **добавить параметр страны**. Гибрид pgvector+FTS+метафильтры. Чинится на стороне LegalX.
- `search_cases` — без изменений, только УЗ (схема court).
- Webhook изменений LegalX → InspectorX (`change_events`) — тоже country-aware.
- Версионирование актов в LegalX.
- Пока контракты не готовы физически — InspectorX работает против моков с той же сигнатурой.

## 7. Что должен содержать План №1 (требования к самому плану)

- **Одна гигантская фаза**: Claude Code получает цель и работает без остановок; план даёт полную ориентацию — контекст, зависимости, границы.
- Внутри фазы — порядок работ с зависимостями (что блокирует что), но без искусственных «стоп-точек», кроме объективных: апрув карты Cartographer, golden set до масштабирования, мёрж миграций в main только когда готовы (автодеплой на прод, отката нет).
- Явные границы: фото-чек — вне плана; кейсы — только УЗ; `docs/IDEAS.md` — не кодировать без решения; после запуска — правило заморозки LAUNCH_CHECKLIST.
- Источники истины и приоритет при конфликте: TARGET_FORMAT (контракт данных §4) → ADR-0002…0005 → этот бриф. Расхождения топологии — верен ADR-0002.
- План должен покрыть: миграции схемы (jurisdiction, календарь, каталог ADR-0004 с HS6+UNSPSC+нац. слои), Build-конвейер (§5), витрину (табы стран, сравнение, общий формат показа, чистка УЗ-специфичной терминологии), календарь+нотификации, контур C, контур D (golden set, трейсинг), точку соединения веток.

## 8. Открытые вопросы (для грил-сессии в Claude Code)

- Одна база LegalX с jurisdiction или отдельные базы на страну — **не решено**, решить на грил-сессии (влияет на контракт `search_norms`).
- Источник норм для Казахстана (откуда данные в LegalX) — на стороне ветки LegalX.
- Механика Google Calendar: свой OAuth-флоу vs .ics-приглашения — решить при проектировании фичи.
- Двухуровневая карта Cartographer: формат мировой таксономии категорий (это же ось сравнения стран) — спроектировать в начале Build.
