# ADR-0005: Контракты экосистемы LegalX / SudX / InspectorX

- **Статус:** принято 02.08.2026
- **Автор решений:** Абдурахмон (фаундер)
- **Связано:** `docs/adr/0002-ecosystem-topology.md` (кто где живёт),
  `docs/adr/0003-agent-flow.md` (кто эти контракты вызывает),
  зеркальная дока на стороне LegalX — `jurisbase/docs/INSPECTORX_INTEGRATION.md`
- **Статус сигнатур:** финализированы решением грил-сессии 02.08.2026 (мастер-план
  мультистрановости, Задача 1). Имена параметров, типы и форма ответа ниже —
  не набросок, а обязательный к реализации контракт; расхождение кода с этим
  текстом — баг документации либо баг реализации, а не вариант трактовки.

## Контекст

LegalX, SudX и InspectorX — три проекта, которые могут вестись параллельно
разными людьми и в разных аккаунтах. Чтобы это было возможно, границы между ними
должны быть описаны раньше кода: пока интерфейс зафиксирован, каждая сторона
двигается со своей скоростью и не блокирует остальные.

ADR-0002 уже развёл проекты по базам (LegalX-БД со схемой `court` для SudX +
InspectorX-БД) и запретил физическую сшивку схем. Настоящий ADR описывает, чем
именно они разговаривают.

---

## Топология данных контрактов

LegalX хранит все юрисдикции — `UZ`, `KZ`, `AE` — в одной базе и одних и тех же
таблицах: разграничение — колонка `jurisdiction` (ISO 3166-1 alpha-2), а не
отдельная схема или отдельный проект Supabase на страну. Изоляция происходит на
уровне каждого запроса (`p_jurisdiction` в `search_norms`, поле `jurisdiction`
в webhook), а не на уровне физической границы БД.

Отсюда запрет: никаких FK, вьюх, функций и триггеров, сшивающих строки разных
юрисдикций друг с другом — акт УЗ не ссылается на акт КЗ, требование одной
страны не джойнится в самой БД с фрагментом другой. Это то же правило, которым
ADR-0002 защищает возможность выделить SudX в отдельный проект («никаких вьюх,
функций и триггеров, физически сшивающих схемы», раздел «Правила, сохраняющие
возможность выделить SudX позже»), применённое не к схеме `court`, а к колонке
`jurisdiction`. Правила отселения — те же: если для одной из стран понадобится
физическая изоляция (регуляторное требование к резидентности данных, рост
нагрузки, отдельный биллинг), выделение делается по стабильному внешнему
идентификатору и не требует правки вызывающей стороны — контракты уже отдают
`jurisdiction` явным параметром/полем, а не подразумевают его через адрес базы.

## Контракт 1. `search_norms(p_query, p_jurisdiction, …)` — поиск норм в LegalX

- **Где живёт:** RPC-функция в Supabase LegalX.
- **Кто вызывает:** воркер InspectorX (контур Build) под **read-only ролью**.
- **Что внутри:** гибридный поиск — pgvector + FTS + метафильтры (домен права,
  дата, статус действия).

```sql
-- RPC в Supabase LegalX, вызывается воркером InspectorX под read-only ролью
search_norms(
  p_query        text,          -- поисковый запрос
  p_jurisdiction text,          -- 'UZ' | 'KZ' | 'AE' (ISO 3166-1 alpha-2), ОБЯЗАТЕЛЕН
  p_domains      text[] default null,  -- метафильтр по доменам права
  p_limit        int default 10
) returns table (
  fragment_id uuid, act_id uuid,
  act_title text,               -- полное название акта
  article_ref text,             -- номер статьи/пункта
  anchor text,                  -- якорь для deep-link на параграф
  content text,                 -- текст фрагмента (uz-оригинал + ru-перевод, если есть)
  act_status text,              -- active | repealed | pending
  valid_from date, valid_to date,
  score float
)
-- Пустой результат = «поиск не нашёл». Семантику «нормы нет в стране»
-- определяет Retriever итеративно (N переформулировок), не RPC.
```

`p_jurisdiction` обязателен без значения по умолчанию — см. «Топология данных
контрактов» выше: одна LegalX-база хранит все страны, и без явного параметра
запрос физически не может знать, какую из них искать.

Реквизиты источника нужны целиком: без них Assembler не соберёт уровень 2
карточки (`TARGET_FORMAT.md` §4), а Verifier не сможет сверить фрагмент с
первоисточником.

**Эволюция без смены контракта:** позже RPC оборачивается в HTTP-эндпоинт на
Railway. Для вызывающей стороны меняется транспорт, не смысл.

**Известное ограничение:** текущая реализация поиска в LegalX некачественная.
Починка — отдельная сессия на стороне LegalX. До неё Retriever/Норма в контуре
Build будет чаще обычного возвращать исход «LegalX не нашёл» (в needs-attention,
не в «требований нет» — см. ADR-0003, решение 5).

## Контракт 2. `search_cases(p_article, p_topic?, …)` — поиск практики в SudX

- **Где живёт:** аналогичная RPC в SudX (схема `court` в базе LegalX).
- **Кто вызывает:** воркер InspectorX при Build, по статье санкции.

```sql
search_cases(p_article text, p_topic text default null, p_limit int default 5)
returns table (case_url text, case_title text, summary text, outcome text, amount numeric)
-- Только УЗ (схема court). Параметра jurisdiction НЕТ намеренно.
```

Параметра `jurisdiction` в контракте нет намеренно, а не по недосмотру: судебная
практика в этой версии — только узбекская (см. глобальные ограничения плана
мультистрановости). Если практика появится для другой юрисдикции — это новый
контракт, а не параметр к этому.

InspectorX **снапшотит топ-5 кейсов в `requirement_details` на этапе Build** —
витрина не ходит в SudX в рантайме. Кнопка на витрине ведёт на страницы SudX.

## Контракт 3. Webhook изменений LegalX → InspectorX (country-aware)

LegalX при изменении акта или фрагмента шлёт HTTP POST (`pg_net`) на
PostgREST-RPC `ingest_change_event` в InspectorX:

```json
{
  "secret": "<из Vault LegalX>",
  "jurisdiction": "UZ",
  "act_id": "<uuid в LegalX>",
  "fragment_ids": ["<uuid>"],
  "change_type": "new | amended | repealed | effective_soon",
  "effective_date": "2027-01-01",
  "summary": "краткое описание изменения"
}
```

`secret` — общий секрет из Vault LegalX, проверяется на входе в
`ingest_change_event`, чтобы эндпоинт не принимал чужие вызовы. `jurisdiction`
обязателен и того же формата, что `p_jurisdiction` в `search_norms`: без него
InspectorX не сможет сопоставить `act_id` с правильной страной в собственных
данных.

**Граница покрытия:** webhook покрывает **только связанные акты** — те, на
которые уже ссылается хотя бы одно требование. Новое регулирование, ни с чем не
связанное, он не поймает по определению: ловит Discovery-джоб InspectorX по cron
(ADR-0003, решение 7).

## Контракт 4. Требование к LegalX — версионирование актов

LegalX обязан вести **историю редакций актов**. Без неё InspectorX не может:

- собрать **provision change history** («было/стало» на карточке требования);
- извлечь **lifecycle-даты** (вступление, переходный период, утрата силы) —
  а из них считается статус действия требования (ADR-0003, решение 8).

Это не пожелание, а условие работоспособности контуров Monitoring и Build.

---

## Последствия

- Три проекта можно вести параллельно: сторона LegalX реализует `search_norms`,
  `search_cases`, webhook и версионирование, сторона InspectorX — воркер,
  Discovery-джоб и Impact-маппер. Точка синхронизации — эти четыре контракта.
- Read-only роль для воркера InspectorX в LegalX-БД — отдельная задача по
  доступам (см. `docs/INFRA_ACCOUNTS.md`).
- Запрет ADR-0002 на вьюхи/функции/триггеры, сшивающие схемы, остаётся в силе:
  контракты — вызовы, а не общие объекты БД. Поэтому выделение SudX в отдельный
  проект не ломает `search_cases`, а только меняет её адрес.
- Зеркальная дока `jurisbase/docs/INSPECTORX_INTEGRATION.md` пишется параллельно;
  при расхождении формулировок стороны сверяются по настоящему ADR.
