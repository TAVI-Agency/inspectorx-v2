# ADR-0003: Агентский флоу контент-фабрики InspectorX

- **Статус:** принято 02.08.2026
- **Автор решений:** Абдурахмон (фаундер)
- **Рабочая детализация:** таблица флоу на 51 строку в Miro —
  https://miro.com/app/board/uXjVJ72tqEY=/?moveToWidget=3458764679731879079
  ADR фиксирует **решения**, Miro — пошаговую детализацию контуров.
- **Связано:** `docs/TARGET_FORMAT.md` §4 (контракт данных требования),
  `docs/adr/0002-ecosystem-topology.md` (где исполняется Python, предохранители
  агентных прогонов), `docs/adr/0005-ecosystem-contracts.md` (интерфейсы к LegalX/SudX)

## Контекст

Контент InspectorX — не текст «о законе», а машиночитаемое требование: правило,
санкция, срок, инструкция. Руками это не наполняется в объёме каталога, а
«одним большим агентом» — не воспроизводится и не отлаживается. Нужен
зафиксированный флоу: какие контуры существуют, кто в них работает, где
проходит граница между детерминированным кодом, LLM и человеком.

ADR-0002 уже задал рамку: агентные прогоны недетерминированны и не пишут в прод
напрямую. Настоящий ADR описывает, как при этой рамке фабрика всё-таки доводит
требование до `published`.

## Решение 1. Четыре контура

| Контур | Что делает | Чем запускается |
|---|---|---|
| **A · Build** | Наполнение карточек требований | **Вручную**, по товарной группе ИКПУ |
| **B · Runtime** | Фото-чек этикетки для пользователя | Событие загрузки фото |
| **C · Monitoring** | Изменения законодательства | Webhook LegalX (event) + cron |
| **D · Инфра** | Eval, трейсинг, дев-задачи смежных проектов | По потребности |

Гранулярность учёта в A — **отдельный айтем-требование**, не группа и не прогон:
статусы, ретраи и публикация трекаются на уровне айтема. Группа — только единица
запуска.

**B·Runtime — обязательная часть MVP**, в обоих каналах: веб и Telegram.

## Решение 2. Оркестрация — гибрид, а не «агент-дирижёр»

- **Скелет пайплайна детерминированный:** state machine, очередь, статусы в БД.
  Порядок шагов, ретраи и переходы — код, не решение модели.
- **LLM-«менеджер исключений»** вызывается только в особых точках:
  N подряд провалов верификации, пробел в coverage, спорный вердикт фото-чека.
- **Человек (владелец) — последний уровень:** разбирает список needs-attention
  пачкой, а не сопровождает каждый айтем.
- **Единственный ручной gate конвейера** — апрув карты айтемов группы перед
  запуском Build. Всё остальное человек видит постфактум: в needs-attention,
  в coverage-отчёте, в очереди ревью (см. `TARGET_FORMAT.md` §5b).

## Решение 3. Generic-агенты с профилями, а не зоопарк уникальных

Базовые роли переиспользуются, специфика задаётся профилем (промпт + схема
ответа + источник):

| Generic-агент | Профили |
|---|---|
| Retriever | Норма · Label · Санкции · Судебные кейсы · Samples · Перевод |
| Verifier | те же |
| Classifier | те же |
| Summarizer | те же |
| Translator | те же |

Спец-роли (единичные, профилями не покрываются):

- **Cartographer** — разовый deep research: карта регуляторных айтемов товарной
  группы. Смотрит, какие типы требований существуют в мировой практике и что
  есть в ~50 бенчмарк-странах, и превращает это в список того, что надо
  проверить в Узбекистане.
- **Question writer** — превращает айтем в вопросы к LegalX и в JSON-схему ответа.
- **Samples judge** — решает, нужны ли для требования шаблоны документов.
- **Template hunter** — веб-поиск шаблонов документов.
- **In-house lawyer** — агент-юрист: суждение о необходимости имплементации и
  инструкция «что делать».
- **Vision agent** — фото-чек этикетки (контур B).
- **Assembler** — сборка карточки по контракту `TARGET_FORMAT.md` §4.

## Решение 4. Verifier независим от producer

- **Другая модель и другой промпт**, чем у агента, породившего текст.
- Verifier видит **вопрос + фрагмент + первоисточник**; рассуждений producer он
  **не видит** — иначе он проверяет логику, а не факт.
- **Fail-политика:** N провалов подряд → айтем остаётся в `draft` и попадает в
  needs-attention. Не публикуем. Ретраи не «дожимают» до pass.

## Решение 5. Конвейер Build — фиксированный порядок

```
карта группы (Cartographer, deep research)
  → АПРУВ ВЛАДЕЛЬЦЕМ (единственный ручной gate)
  → Question writer          айтем → вопросы к LegalX + JSON-схема ответа
  → Retriever/Норма          итеративный поиск через RPC search_norms
  → Verifier
  → Summarizer (суть) → Verifier
  → Classifier (категория: маркировка / упаковка / …) → Verifier
  → Rule-maker → Verifier    ← критическая точка
  → Scope-резолвер           привязка к кодам каталога
  → Lifecycle-экстрактор     даты вступления / переходного периода / утраты силы,
                             отменяющий акт
  → санкции:  Retriever → Verifier → структуризатор
  → кейсы:    Retriever в SudX → Verifier → саммаризатор кейса
  → Samples judge → Template hunter → Verifier
  → In-house lawyer
  → Translator uz → Verifier перевода
  → дедупликация             эмбеддинги + Classifier на спорных
  → Assembler                карточка по контракту TARGET_FORMAT §4
  → загрузка в БД (draft)
  → Coverage checker         карта vs факт, отчёт владельцу
  → публикация               все верификации pass → published
```

Что важно в отдельных шагах:

- **Retriever/Норма различает два исхода:** «нормы в УЗ нет» и «LegalX её не
  нашёл». Второе — не отсутствие требования, а дефект поиска, поэтому идёт в
  needs-attention, а не в «требований нет».
- **Rule-maker** превращает текст нормы в машинно-проверяемое правило:
  `{поле: состав, язык: uz, обязательно: да}`, `{штрих-код: EAN-13}`.
  Верификация здесь **критическая**: кривое правило = кривой pass/fail
  пользователю на фото-чеке, а не просто неточный абзац.
- **Структуризатор санкций** переводит текст в `{статья КоАО, штраф в БРВ, мера}`.
- **Кейсы:** Retriever ищет в SudX по статье санкции, берёт топ-5 и **снапшотит
  ссылки на этапе Build** — витрина не ходит в SudX в рантайме.
- **Translator uz переводит только ИИ-тексты.** Официальные текстовки приходят
  из LegalX уже с переводом и не переводятся повторно.
- **Assembler** раскладывает по пейволлу: тизер → `requirement_contents`,
  платное (санкции, кейсы, шаблоны, инструкция) → `requirement_details`.
  Пустой блок → «Данных пока нет».
- **Coverage checker** сверяет карту группы с фактом: закрыто / драфт / не
  найдено — и отдаёт отчёт владельцу.

## Решение 6. Runtime — фото-чек этикетки

**Чек-лист лейбл-чека (шаг A.4) — производный артефакт.** Он не пишется руками:
генерируется из машинных правил группы и **версионируется** — изменились правила,
появилась версия vN+1.

Поток:

```
приём фото
  → проверка качества (размыто / темно → «переснимите»)   скрипт + CV
  → детекция зон (этикетка / штрих-код / знаки)
    + OCR uz/ru + декодирование штрих-кода
  → Vision agent: вердикт по пунктам (pass / fail / unreadable)
    + аннотированное фото + «что делать»
  → эскалация unreadable / low-confidence в needs-attention
```

Вердикт **хранит версию чек-листа**, по которой он вынесен. Это то, что позже
позволяет сказать пользователю: «вы проверялись по старой версии — перепроверьте»
(см. решение 7).

## Решение 7. Monitoring — изменения законодательства

```
LegalX: изменился СВЯЗАННЫЙ акт/фрагмент → webhook
  → change_events
  → Impact-маппер
  → requirement_change_impacts + flagged_by_change (карточка остаётся на витрине)
  → provision change history (скрипт)
  → In-house lawyer: нужно ли ре-ревью → частичный Build
  → перегенерация чек-листа лейбл-чека
  → user_notifications
```

Уведомления включают отдельный тип: «этикетка проверялась по старой версии
чек-листа — перепроверьте».

Два дополнительных источника, не покрытых webhook'ом:

- **Cron переходов статуса** — ловит наступление дат lifecycle (см. решение 8).
- **Discovery-джоб (cron)** — новые акты LegalX ни с чем не связаны, поэтому
  webhook по ним не сработает вообще. Джоб прогоняет вопросы Cartographer по
  свежим поступлениям и заводит кандидатов-айтемов в `draft`.

## Решение 8. Статус действия требования — вычисляемое поле

В БД хранятся **только даты** (lifecycle: вступление, переходный период, утрата
силы, отменяющий акт). Статус `upcoming / in_force / transitional / expiring /
repealed` **считает код на лету** — текстом он не хранится и не может разойтись
с датами.

- Assembler кладёт в `requirement_details` бейдж + пояснение юриста.
- Cron ловит переходы дат и шлёт уведомления вида «требование вступило в силу».

## Решение 9. Модели и стоимость

GPT через API. Тиры — по ролям, а не по контурам:

| Тир | Роли |
|---|---|
| Дешёвый | Classifier, Summarizer, Translator |
| Средний | Retriever, Vision, Rule-maker |
| Дорогой | Verifier, In-house lawyer, deep research, менеджер исключений |

Финальный выбор конкретных моделей — **по данным трейсинга после первых
прогонов**, не заранее.

До масштабирования обязательны:

- **golden set ~20 требований**, размеченных вручную;
- **трейсинг стоимости по ролям** (какая роль сколько сжирает).

## Последствия

- Схема БД получает уровень учёта на айтем-требование: статус, счётчик ретраев,
  признак needs-attention. Это отдельная миграция.
- Правило «ни одна карточка не публикуется без человека» (`TARGET_FORMAT.md` §5b)
  сохраняется: автопубликация возможна только после того, как все верификации
  дали pass, а очередь ревью остаётся поверх этого.
- Чек-лист лейбл-чека нельзя редактировать руками — он производный; правки
  вносятся в машинные правила требования.
- Контур A зависит от контрактов `search_norms` / `search_cases` и webhook'а
  изменений (ADR-0005). Пока поиск в LegalX некачественный, Retriever/Норма будет
  давать высокую долю исходов «LegalX не нашёл» → needs-attention.
