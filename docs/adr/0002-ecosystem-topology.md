# ADR-0002: Топология экосистемы — названия, базы, облако

- **Статус:** принято 02.08.2026, действует с запуска 03.08.2026
- **Автор решений:** Абдурахмон (фаундер)
- **Заменяет:** разрозненные формулировки в `docs/ARCHITECTURE_FLOW.md`,
  `docs/INFRA_ACCOUNTS.md`, `docs/ROUTINES.md`, `README.md`
- **Связано:** `docs/ECOSYSTEM_LAUNCH_2026-08-03.md` (чек-лист запуска)

## Контекст

К 02.08.2026 экосистема описана в документах непоследовательно: продукт законов
называется JurisBase, судебная практика фигурирует то как «раздел», то как отдельный
продукт, число баз Supabase колеблется между двумя и тремя, место исполнения Python-кода
записано в трёх версиях (Railway / serverless GPU / Claude-рутины). Перед публичным
запуском нужен один документ, на который ссылаются все остальные.

## Решение 1. Названия

| Было | Стало | Что это |
|---|---|---|
| JurisBase | **LegalX** | Публичная платформа законов: скрапинг lex.uz, редакции, переводы, диффы |
| — | **SudX** | Судебная практика. **Раздел внутри LegalX**, не отдельный продукт |
| InspectorX | **InspectorX** | Без изменений. B2B-витрина требований, основная выручка |
| ImportEase | — | Название мёртвое, не использовать |

Старое имя JurisBase остаётся только там, где переименование ломающее и требует
отдельной миграции: значение `change_source = 'jurisbase'` и колонка `jurisbase_act_id`
в `supabase/migrations/20260711120000_initial_schema.sql`, производные от них типы в
`src/lib/database.types.ts`, переменные `JB_*` в `.env.importer`. Их трогать только
вместе с миграцией и после запуска.

## Решение 2. Supabase — два проекта в одной организации, один аккаунт

**Два проекта:**

1. **LegalX-БД** (`atcogcwowfqzzzgbbjer`) — акты, редакции, переводы, диффы
   **плюс схема `court`** с судебной практикой (SudX).
2. **InspectorX-БД** (`kcjlrvgjtoefqgzxuizz`) — требования, товары, услуги, пользователи
   витрины, подписки, схема `pipeline`.

Оба — в **одной организации на одном Google-аккаунте владельца**, тариф Pro.
Подтверждено владельцем 02.08.2026.

**Почему SudX — схема, а не третий проект:**

- **Auth живёт внутри проекта.** Отдельный проект = отдельная таблица пользователей.
  Пользователь LegalX для SudX был бы незнакомцем; штатного способа шарить сессию между
  проектами нет. Вход в экосистеме должен быть один.
- **Джойнов между базами нет.** Ценность SudX — «вот пункт акта, вот как его трактовал
  суд». Это джойн. Между двумя проектами он превращается в FDW или склейку в приложении
  на каждый запрос.
- Цена вопроса ($10/мес за проект) на решение не влияет — влияет сложность.

**Почему LegalX и InspectorX всё-таки раздельно:** разные жизненные циклы данных, разные
модели RLS, разный профиль нагрузки; связь между ними батчевая — через воркер конвейера,
а не на каждый пользовательский запрос.

**Почему один аккаунт:** Pro стоит $25/мес за организацию, первый проект включён,
следующий от $10 — итого $35 за два. Три отдельных аккаунта = минимум $75. Важнее денег:
100 000 MAU и 250 ГБ egress включены **на организацию** и пулятся между проектами, а не
режутся. Плюс одна карта, один MFA, один набор бэкапов. Отдельный аккаунт оправдан только
при продаже продукта другому собственнику.

### Правила, сохраняющие возможность выделить SudX позже

Обязательны к соблюдению с первой миграции схемы `court`:

1. Таблицы `court` ссылаются на акты по **стабильному внешнему идентификатору**
   (`act_id` + label юнита), а не только через FK.
2. **Никаких вьюх, функций и триггеров, физически сшивающих схемы.** Соединение —
   только на уровне запроса приложения.
3. Отдельный каталог миграций и отдельный набор RLS-политик для `court`.

При соблюдении этих правил выделение = `pg_dump -n court` в новый проект.

**Триггеры выделения** (любой из трёх): корпус решений начал мешать latency LegalX;
у SudX появилась своя регистрация и биллинг; SudX выделяется как самостоятельный продукт.

## Решение 3. Python и агенты — на Railway, не в Supabase

**Supabase Edge Functions для этого не годятся:** рантайм Deno/TypeScript, Python не
поддерживается вообще; лимиты 256 МБ памяти, 2 с CPU на запрос, 400 с wall clock на
платном тарифе, 20 МБ на функцию. Скрапер lex.uz не влезает ни по языку, ни по времени.

**Роль базы в запуске работы** — только разбудить воркер: `pg_cron` для расписаний внутри
БД и `pg_net` для HTTP-вызова наружу. `pg_net` уже используется в
`20260727120000_lead_notifications.sql`.

**Railway** — план **Hobby** ($5/мес, включено $5 потребления), два проекта:

| Проект | Сервисы |
|---|---|
| `legalx-workers` | Скрапер lex.uz, PDF Lab, переводчик, DiffEngine, arq-воркер, Redis, cron |
| `inspectorx-workers` | Импортёр конвейера, Telegram-бот, Doc-checker, Vision-инференс |

Обе цены Railway — минимумы, целиком идущие в счёт потребления: при потреблении ниже $20
Hobby дешевле, выше — платы совпадают. Переход на Pro ($20) делается, когда счёт стабильно
превышает $20; тогда он даёт 30-дневные логи вместо 7, поддержку Railway и 99.99%.

**Volume Railway не использовать под данные.** На Hobby его 5 ГБ. Сканы, фото упаковок,
PDF-отчёты — в объектное хранилище (Cloudflare R2 или Supabase Storage). Веса
CV-моделей — вшивать в образ.

## Решение 4. Скрипты и агенты — разные сущности

| Тип работы | Где исполняется | Почему |
|---|---|---|
| Скрапинг, diff редакций, перевод по глоссарию, импорт отчётов | Railway: обычный Python + arq + cron | Детерминированно, идемпотентно, воспроизводимо, дёшево, есть логи и откат |
| Реакция на изменение строки в БД | pg-триггер + `pg_net` → HTTP в Railway | Уже работает на уведомлениях о заявках |
| «Найти, где вообще лежат нужные данные» — агентный ресёрч | Контейнер на Railway с ключом Anthropic API, либо Claude-рутина | Задача недетерминированная, скриптом не решается |
| Инференс CV (Vision) | Railway CPU | См. решение 5 |

**Агентные рутины не являются продакшн-конвейером.** Результат недетерминированный,
стоимость прогона токенная, идемпотентности нет, отладка и откат затруднены. Их выход
идёт человеку или в очередь ревью, но **не пишется в прод напрямую** — это следствие
правила «ни одна карточка не публикуется без человека».

**Обязательные предохранители до первого агентного цикла:** лимит трат в консоли
Anthropic; логирование стоимости каждого прогона в БД; prompt caching на всё повторяемое;
лимит трат в Railway.

## Решение 5. Vision (фотоконтроль упаковки) — внедряем, инференс на Railway CPU

Vision переходит из статуса «не в запуске» в **принятую фичу продукта**. Отменяет пункт
«Vision» в списке «осознанно не делаем» из `ECOSYSTEM_LAUNCH_2026-08-03.md` — но
**не для ночи запуска**: внедрение идёт отдельным треком после 03.08.

- Инференс — **Railway CPU**, не serverless GPU. Ядро по спеке — YOLO nano/small +
  OCR + декодер штрих-кода + rule-engine; всё это CPU-совместимо, ~2–6 с на снимок,
  чего достаточно для асинхронного воркера.
- Modal/RunPod в `ARCHITECTURE_FLOW.md` понижается со статуса «плановое решение» до
  «запасной вариант при росте объёма или требований к latency».
- Обучение остаётся локальным — Railway GPU не предоставляет.
- Фото — в объектное хранилище, не в контейнер.
- Репозиторий `inspector-vision` остаётся отдельным; интеграция с InspectorX — через
  таблицы результатов проверки и очередь arq.

## Решение 6. Vercel — Pro, два фронта

Оба фронта в одном Pro-аккаунте. SudX **не получает отдельного домена сейчас**: домен
куплен, но не одобрен, поэтому SudX живёт внутри LegalX (путь или поддомен) и переезжает
на свой домен, когда одобрение придёт. Отдельного фронта под SudX на запуске нет —
значит, «три фронта» в чек-листе запуска исправляются на два.

Замечание из `docs/SERVICES_HANDOFF.md` про Hobby-блок Vercel и подпись коммитов
на Pro-плане неактуально.

## Решение 7. Наблюдаемость — Sentry да, SonarQube нет

- **Sentry ставится до анонса.** Это ~15 минут на фронт: пакет, DSN в переменных
  окружения, инициализация в точке входа. Бесплатного тарифа хватает. Без него первые
  сутки публичного трафика — единственный шанс увидеть реальные поломки — проходят вслепую.
- **SonarQube и подобный статический анализ — нет.** Он ищет качество кода, а не
  инциденты у живых пользователей; на запуске не решает ни одной задачи. `oxlint`
  и `tsc -b` в `npm run build` эту роль уже закрывают.
- Аналитика продукта (PostHog/Plausible) — отдельный обязательный пункт, Sentry её
  не заменяет.

## Последствия

- `docs/ARCHITECTURE_FLOW.md` перестаёт быть источником по инфраструктуре в части
  названий, числа баз и места инференса — эти вопросы решает настоящий ADR.
- Схема `court` требует отдельной миграции и отдельного набора RLS — задача после запуска.
- Переименование `jurisbase_*` в схеме БД и типах — отдельная миграция, не в запуск.
- `docs/ROUTINES.md` («автоматизация отложена») остаётся в силе для агентных рутин,
  но не распространяется на детерминированные воркеры Railway — их можно поднимать
  без ожидания «идеального формата процесса».
