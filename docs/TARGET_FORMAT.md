# InspectorX — целевой формат продукта (Target Format)

> **Статус:** зафиксирован как целевой ориентир 11.07.2026 (сессия брейнсторма Абдурахмон + Claude).
> **Назначение:** единый источник истины о том, ЧТО пользователь видит в конечном продукте.
> Технические решения (БД, пайплайны, LLM) подчиняются этому документу, а не наоборот.
> **Как читать:** пометка [ПРОВЕРЕНО] = подтверждено практикой мировых эталонов (см. §9), строить смело.
> Пометка [ГИПОТЕЗА] = наше предположение, проверить на первых 10-20 пользователях, готовность изменить.

---

## 1. Позиционирование одним предложением

InspectorX — не «справочник законов по товару», а **«чек-лист соответствия моего бизнеса»**.

Справочник отвечает на вопрос «что написано в законе». Чек-лист отвечает на вопрос
«что мне делать, к какому сроку, какими документами и что будет, если не сделать».
Каждое продуктовое решение проверяется этим тестом: приближает ли оно ответ на второй вопрос.

---

## 2. Шесть принципов (решения, принятые в этой версии)

### П1. Единый вид для всех в MVP; персонализация по роли — v2 [РЕШЕНИЕ 11.07.2026]
Продукт строится вокруг товара/услуги, а не вокруг персонажа. В MVP все пользователи видят
одинаковую полную картину требований (вкладки процедур как навигация по операциям).
Персонализация («я импортёр — покажи только моё», маршруты, вопросник контекста) —
зафиксирована как идея v2 (см. §10). Атрибут «кому адресовано» (П6) при этом собирается
и показывается на карточках с первого дня — он нужен и без фильтрации.

### П2. Паспорт соответствия сверху [ПРОВЕРЕНО — паттерн executive summary]
Первый экран страницы товара отвечает за 5 секунд: сколько требований для меня,
сколько документов собрать, максимальная санкция, что изменилось за 30 дней,
индекс сложности, дата последней проверки актуальности. Никогда не «выберите требование слева».

### П3. Сканируемый список вместо дерева папок [ПРОВЕРЕНО — Access2Markets, Practical Law]
Единица списка — требование, а не категория. Каждая строка самодостаточна:
заголовок-глагол + тип + адресат + ведомство + санкция одной строкой + статус изменения.
Категории — это фильтры-чипы, а не навигационные папки, которые надо раскрывать вслепую.

### П4. Слой изменений вживлён в карточки [ПРОВЕРЕНО — regtech RCM: Regology, 4CRisk]
Изменение законодательства отображается там, где живёт требование, а не только в колокольчике:
непрочитанная точка на строке → бейдж «изменилось {дата}» → блок «было/стало» в карточке →
«История изменений (N)» в панели источника. Отдельно показываются **будущие** изменения:
«ужесточится с 01.09» (источник — принятые, но не вступившие акты; позже — проекты НПА).
Это прямая реализация ТЗ: «непрочитанное уведомление на каждом субразделе».

### П5. Карточка отвечает «что делать»; цитата закона — рядом, но вторична
[ПРОВЕРЕНО — Practical Law: plain language первичен, источник по ссылке; Stripe: правая синхронная панель]
Порядок блоков: суть → как исполнить (шаги, сроки, стоимость) → документы → ведомство →
санкция с суммой и статьёй → FAQ → задать вопрос / GR. Verbatim-цитата — в правой панели,
с точной ссылкой на пункт акта и редакцию (не на весь документ).

### П6. «Кому адресовано» — обязательный атрибут каждого требования [ПРОВЕРЕНО — LegalRuleML applicability]
Первый вопрос бизнеса: «это про меня?». Требование без атрибута роли
(производитель / импортёр / продавец / перевозчик) не публикуется.

## 3. Экран «Страница товара» (главный экран продукта)

Сверху вниз:

1. **Шапка-паспорт**: название товара · коды (ТН ВЭД **и** ИКПУ) · ссылка «изменить контекст»
   · бейдж «проверено {дата}» · сложность N/10.
2. **Сводка (4 метрики)**: требований для вас · документов собрать · макс. санкция · изменений за 30 дней.
3. **Фильтры-чипы**: «Мой маршрут: {операция}» (активен по умолчанию) + этапы ЖЦ
   (сертификация, маркировка, реализация, …). На чипе — счётчик непрочитанных изменений.
4. **Список требований** (строки по §4, уровень 0), сгруппирован по этапам ЖЦ.
5. **Раскрытая карточка** (уровень 1 + правая панель уровня 2, по §4).

Правила отображения:
- **Пустые разделы не показываются вообще** [ПРОВЕРЕНО — правило Access2Markets].
  Никаких заглушек «информация будет добавлена позже». Нет данных — нет блока.
- Языковой переключатель UZ / RU / EN действует на контент; verbatim всегда доступен
  в оригинале (UZ) параллельно с переводом.
- Экспорт всей страницы в PDF-чек-лист [ПРОВЕРЕНО — Global Trade Helpdesk].

## 3b. Экран поиска (входная дверь продукта) [РЕШЕНИЯ 11.07.2026]

1. **Охват с первого дня: товары + услуги.** Переключатель типа поиска:
   «Товар (ТН ВЭД/ИКПУ)» · «Услуга (ИКПУ)» · «Вид деятельности (ОКЭД)».
   Услуга — отдельный тип паспорта: без импорта/транзита, с лицензиями и разрешениями
   (структуру паспорта услуги спроектировать отдельно — открытая задача).
2. **Поиск кода — гибрид:**
   - по умолчанию: строка поиска с автоподсказками (текст / код / штрих-код),
     алиасы и «возможно, вы имели в виду» (уже есть в текущей версии — сохранить);
   - при неоднозначности (несколько существенно разных кодов): предложение
     «Не уверены, какой ваш? Ответьте на 2 вопроса» → AI-уточнение → точный код.
     Прецедент паттерна: вопросник на tasnif.soliq.uz;
   - запасной путь: дерево каталога (браузинг по категориям, как Access2Markets).
   - Правило: неверный код = все требования ниже неверны, поэтому у результата поиска
     всегда показываем полное официальное название кода + родительскую категорию,
     чтобы пользователь мог сам заметить ошибку.
3. **Частичный контент показываем честно.** Если по товару наполнена часть требований:
   показываем что есть + явная пометка на ненаполненных этапах «раздел в работе»
   (отличать «требований нет по закону» от «мы ещё не наполнили» — это разные состояния!).
   Полностью пустой товар: показываем горизонтальные требования (применимые ко всем товарам)
   + пометка + возможность оставить заявку «уведомить, когда готово».
4. Поиск ведёт и по алиасам на 3 языках (uz/ru/en + латиница/кириллица для узбекского).

## 3a. Экран «Мои товары + лента изменений» (второй ключевой экран)

Сверху вниз:

1. **Сводка недели**: «За неделю: N изменений · M требуют действий до {дата}».
2. **Портфель товаров** (карточки): название · код · счётчик непрочитанных · статус одной строкой
   («дедлайн 01.09» / «действий не требуется» / «без изменений 30 дней»).
3. **Лента изменений** — карточка изменения содержит:
   - индикатор непрочитанного + бейдж важности (важно / средняя / низкая — по AI-оценке);
   - привязку: товар · этап ЖЦ · дата;
   - заголовок изменения человеческим языком (не «изменился документ №X»);
   - блок **Было / Стало** (для важных изменений);
   - **срок**: «вступает в силу {дата} — осталось N дней» или «уже действует»;
   - **что делать** одной строкой (или «ничего — изменение в вашу пользу»);
   - действия: «К требованию» · «Сравнить редакции» · «Отметить прочитанным».
4. **Проекты НПА** — отдельный, визуально приглушённый тип карточки: «обсуждается»,
   ссылка на общественное обсуждение (СОВАЗ), без пугающих бейджей — ещё не право.
   [ГИПОТЕЗА] — фича «узнать до принятия» может быть главным wow-фактором, но требует
   парсинга regulation.gov.uz; в MVP можно ограничиться принятыми-но-не-вступившими.
5. **Настройка дайджеста**: email еженедельно / Telegram мгновенно.

Правила:
- Изменение всегда формулируется как изменение ТРЕБОВАНИЯ к товару пользователя,
  а не как изменение документа.
- Позитивные изменения помечаются явно («в вашу пользу») — снижает тревожность продукта.
- Счётчики непрочитанного каскадируются: лента → карточка товара → строка требования.

## 4. Анатомия требования — три уровня раскрытия

Это контракт данных: карточка не публикуется без полей уровня 0.

### Уровень 0 — строка в списке (виден всегда)
| Атрибут | Пример | Обязателен |
|---|---|---|
| Заголовок-глагол | «Получить ветеринарный сертификат до ввоза» | да |
| Тип (деонтика) | обязанность / запрет / разрешение-льгота | да |
| Адресат (роль) | импортёр | да |
| Ведомство | Комветнадзор | да |
| Санкция одной строкой | «штраф до 50 БРВ» | да (или «санкция не установлена») |
| Статус | действует / изменилось {дата} / изменится с {дата} | да |
| Индикатор непрочитанного | точка | автоматически |

### Уровень 1 — раскрытая карточка
- Описание простым языком (2-4 предложения).
- **Как исполнить**: нумерованные шаги + срок + стоимость (гос. пошлина/БРВ).
- **Документы**: каждый документ — отдельный элемент (что, где взять).
- Ведомство + контакты («к кому идти»).
- Полные санкции: сумма + статья (КоАО/НК) + что ещё грозит (возврат партии и т.п.).
- FAQ по этому требованию.
- Действия: «Задать вопрос» · «Официальный запрос (GR)» · «Скачать чек-лист».

### Уровень 2 — юридический слой (правая панель / второй клик)
- Verbatim-цитата точного пункта (не всего акта), UZ-оригинал + перевод.
- Реквизит источника: акт, пункт, действующая редакция, дата.
- «История изменений (N)» этого требования: было/стало по датам.
- «Открыть акт» — deep-link на параграф в JurisBase.
- [ГИПОТЕЗА] Обоснование применимости: «почему это требование привязано к вашему коду»
  (паттерн Avalara rationale) — ценно для доверия, проверить, читает ли кто-то.

## 5. Слой изменений (сквозной)

- Подписка пользователя = его товары (избранное) + сохранённые контексты.
- Каскад непрочитанного: товар → этап ЖЦ → требование (бейджи со счётчиками).
- Карточка изменения: **что изменилось** (было/стало) → **важность** → **что делать** →
  **дедлайн вступления**. Не «изменился документ №X», а «изменилось требование Y к вашему товару».
- Каналы: in-app (обязательно), email-дайджест, Telegram [ГИПОТЕЗА по приоритету каналов —
  спросить первых пользователей, что реально читают].

## 5a. Три уровня ответа: AI → эксперт → госорган [РЕШЕНИЯ 11.07.2026]

Воронка вопросов пользователя — три ступени, каждая следующая дороже и авторитетнее:

| Ступень | Кто отвечает | Скорость | Гарантия | Метка на ответе |
|---|---|---|---|---|
| 1. AI-разъяснение | RAG по опубликованным карточкам + актам | мгновенно | нет | «AI-ответ, не юр. консультация» |
| 2. Эксперт | юрист команды | 1-2 раб. дня | професс. мнение | «Проверено юристом {дата}» |
| 3. GR-запрос | официальный ответ госоргана | 15-30 дней (закон об обращениях) | максимальная | «Официальный ответ {орган}» |

Правила ступени 1 (AI):
- Отвечает ТОЛЬКО на основе опубликованных карточек и связанных с ними актов, всегда с citation.
- Не уверен / нет источника → честно говорит «не могу подтвердить» и предлагает ступень 2.
  Никогда не досочиняет.
- Если затронутое требование в статусе «проверяется обновление» — сообщает об этом.
- Вне регуляторной тематики не отвечает.

Правила ступени 3 (GR):
- Статусы запроса в кабинете: черновик → отправлено → в работе органа → получен ответ.
- Полученный официальный ответ прикрепляется к требованию и — обезличенно — обогащает FAQ
  этого требования для всех пользователей. Каждый GR-запрос делает продукт умнее.

Слой доверия (сквозной): каждый контентный блок несёт одну из трёх меток —
«AI-черновик» / «Проверено юристом {дата}» / «Официальный ответ». Пользователь всегда видит,
какого уровня информации он касается. [ПРОВЕРЕНО — Practical Law живёт на maintained-метках]

Дисклеймер: InspectorX — информационный сервис, не юридическая консультация.
Короткая версия — постоянно у AI-ответов; полная — в оферте. Формулировку согласовать с юристом.

## 5b. Кухня контента (HITL-админка) [РЕШЕНИЯ 11.07.2026]

Жизненный цикл карточки требования:

```
AI-генерация → draft → [confidence ≥ порога?] → очередь ревью → правка → published
                                                      ↑
источник изменился (diff) → flagged_by_change → re_review (авто-возврат)
```

- **Ни одна карточка не публикуется без человеческого ревью.** Confidence-скор определяет
  приоритет и глубину проверки, а не право на автопубликацию.
- **Экран ревьюера**: очередь с приоритетами → карточка с подсветкой изменений →
  правка полей → publish. Каждое действие логируется (кто/когда/что) — аудит-след.
- **Приоритет очереди наполнения**: (1) заявки пользователей «не нашли товар/раздел в работе»,
  (2) карточки, затронутые изменениями законов, (3) горизонтальные требования
  (применимые ко всем товарам — максимальный охват на единицу труда), (4) новые вертикали.
- **Публичная честность**: когда карточка в re_review после изменения источника,
  на витрине она видна со значком «проверяется обновление» — не скрываем и не показываем
  устаревшее как актуальное.
- Роли: admin / reviewer (юрист) / content-operator. Ревьюер MVP — определить
  (кандидат — дядя как доменный эксперт; вопрос открыт).

## 6. Что сохраняем из текущего InspectorX (уже правильно)

- Ось продукта: поиск → код → требования. Не менять.
- Master-detail layout (список слева, детали справа).
- Состав контентных полей карточки: описание / цитата / источник / рекомендация / санкции / FAQ —
  поля верные, они просто не выведены на уровень списка и частично пустуют.
- Форма «Задать вопрос» с опциями (юр. экспертиза / официальное обращение / срочно) —
  это готовый GR-механизм, оставить как есть.
- Индекс сложности N/10 — развернуть в сводку паспорта.
- Иерархия ТН ВЭД + алиасы поиска + «возможно, вы имели в виду».

## 7. Что уходит / меняется

- 7 вкладок как первый экран → «мой маршрут» по контексту (вкладки — вторичный режим).
- Дерево категорий как навигация → категории-фильтры + плоский сканируемый список.
- Заглушки «будет добавлено» → скрытие пустых блоков.
- Глобальные уведомления без привязки → персональные, привязанные к требованию и товару.
- Одноязычный контент → UZ/RU/EN на уровне каждого контентного поля.
- Только ТН ВЭД → двойная индексация ТН ВЭД + ИКПУ (ИКПУ-санкции — 1% от реализации —
  делают её обязательной для внутреннего рынка, не только ВЭД).

## 8. Открытые вопросы (проверить на пользователях, не решать в споре)

1. [ГИПОТЕЗА] Вопросник контекста в начале: 3 вопроса — норм, 5+ — отвал. Замерить.
2. [ГИПОТЕЗА] Метрика «макс. санкция» в паспорте: пугает или мотивирует? A/B на пилоте.
3. [ГИПОТЕЗА] Нужен ли «режим юриста» (старое дерево + вкладки) в MVP или отложить.
4. [ГИПОТЕЗА] PDF-чек-лист: реально скачивают или хватает веб-версии.
5. Какую вертикаль наполнять первой — ту, которую дядя может валидировать как эксперт.

## 10. Дальнейшие идеи (v2, зафиксировано — не делать в MVP)

- **Персонализация по роли/операции**: контекст «кто вы, что делаете» → «мой маршрут»,
  вопросник gov.uk-style, фильтрация под персонажа. Решение 11.07.2026: MVP показывает
  всем одинаково, продукт строится вокруг товара/услуги.
- **Паспорт услуги** как отдельный тип (лицензии, разрешения, СЭС для деятельности) —
  структура не спроектирована, нужен отдельный заход.
- **Маркетплейс услуг в кабинете** («Проверка маркировки», «Проверка договора», GR-услуги…) —
  переосмыслить состав: какие услуги реально нужны и что можем выполнять; текущий список
  из кабинета — черновик.
- **Аналитика в кабинете** — переосмыслить: какая аналитика полезна пользователю
  (не графики ради графиков; кандидаты: динамика изменений по моему портфелю,
  сроки дедлайнов, история моих GR-запросов).
- Сравнение юрисдикций (Export Navigator), API для интеграций, white-label.

## 11. Эталоны, на которых основаны решения

- **EU Access2Markets / My Trade Assistant** — структура выдачи по HS-коду, скрытие пустых
  разделов, документы как отдельные карточки.
- **GOV.UK** — smart answers (вопросы → персональный список), step-by-step navigation.
- **Thomson Reuters Practical Law** — plain language первичен, метаслой доверия
  (maintained-бейдж, история ресурса), ссылки на первоисточники.
- **Stripe docs** — правая синхронная панель (у них код, у нас verbatim), progressive disclosure.
- **ITC MACMAP / UNCTAD MAST** — таксономия из 178 типов нетарифных мер как основа типологии требований.
- **LegalRuleML** — скелет требования: деонтика + применимость + санкция + временные рамки + источник.
- **Regology / 4CRisk (regtech RCM)** — конвейер «diff источника → затронутые требования → уведомления».
- **Avalara** — хранение rationale применимости кода.
