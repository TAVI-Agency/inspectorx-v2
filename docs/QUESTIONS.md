# QUESTIONS — вопросы, требующие решения Абдурахмона

> Заполняется фронтенд-сессией 11.07.2026. Формат: вопрос → как обошлись сейчас.

## Данные / схема

1. **У `products` нет колонки ИКПУ** (только `hs_code`), хотя TARGET_FORMAT §3 требует
   в шапке-паспорте оба кода (ТН ВЭД **и** ИКПУ).
   *Обход:* для реальных товаров показываю только ТН ВЭД; для мок-товаров показываю мок-ИКПУ,
   чтобы демонстрировать целевой вид. Нужна колонка `ikpu_code` (или таблица соответствий).

2. **`sanction_summary` пуст у всех 203 перенесённых требований** — контракт уровня 0
   («санкция одной строкой — обязательна») нарушен контентом, не схемой.
   *Обход:* пустая санкция в строке не рендерится (правило «пустое не показываем»),
   вместо неё ничего. Надо заполнить в контенте (конвейер/админка).

3. **`authority_id` не заполнен у большинства требований** («ведомство» — обязательный
   атрибут уровня 0 по §4).
   *Обход:* сегмент ведомства скрывается, если null. Заполнить контентом.

4. **Акты из v1 грязные**: `title` вида «1. ПКМ-290, ТР\n2. ПКМ-43 (пункт 66*1)» и
   «Источник не указан (перенос из v1)», `number`/`act_type`/`adopted_date` = null.
   *Обход:* показываю title как есть (первой строкой), реквизитная таблица выводит
   только заполненные поля. Нормализовать акты при чистке контента.

5. **Имена товаров — сырые строки классификатора** («2404 11 000 1 | содержащая…»).
   *Обход:* человекочитаемое имя беру из default-алиаса `search_aliases` (IQOS, Молоко),
   официальное название кода показываю рядом (это и требует §3b п.2 — для самопроверки кода).
   ОК ли такое правило именования?

6. **`requirement_contents.title` — не глаголы** («Информация о сертификации» вместо
   «Указать информацию о сертификации») — контракт «заголовок-глагол» нарушен контентом.
   *Обход:* показываю как есть. Править в контенте.

## Продукт

7. **Полный вид реальных данных сигарет** (details/цитаты за пейволлом) анонимному фронту
   недоступен по RLS — это правильно. Для демо клиенту нужен реальный аккаунт с
   `profiles.is_subscribed = true` (флаг ставится только service-role'ом).
   *Статус:* демо-аккаунт (креденшлы — у владельца, вне репозитория)
   ЗАРЕГИСТРИРОВАН, но включить ему подписку из сессии нельзя (запись в прод
   service-ключом заблокирована политикой). **Нужно руками, 2 минуты:**
   Dashboard → Authentication → Users → подтвердить email демо-аккаунта;
   Table Editor → profiles → у этого юзера `is_subscribed = true`.
   После этого вход под демо-аккаунтом показывает реальные details/цитаты сигарет.
   Тот же ручной путь — для первых платящих клиентов до подключения Click.

8. **Email-подтверждение в Supabase Auth** — ТЗ требует регистрацию без подтверждения;
   это настройка проекта (Dashboard → Auth), кодом не выключается. Проверить/выключить.

9. **Грязь в перенесённом контенте сигарет** (нашёл арт-директорский аудит):
   2 строки с заголовком-заглушкой «none», ~24 полных дубля
   (одинаковые заголовок+этап+тип+роли: пары 084/085, 090/091, тройки 106–108…),
   опечатки («Требования к сырье», «пасспортный»).
   *Обход:* фронт фильтрует заглушки и схлопывает точные дубли — на витрине
   у сигарет теперь 177 требований, а не 203. Правильное место чистки —
   контент/конвейер: дубли надо мержить в базе, опечатки править в админке.

10. **Тизер карточки: ТЗ обещает «описание + источник» бесплатно, но RLS закрывает
   `requirement_details` (там описание) и `requirement_citations`/`act_paragraphs`
   (там источник) целиком.** Аноним фактически видит только уровень 0.
   *Обход:* карточка анонима = уровень 0 + пейволл-блок.
   Если тизер важен — перенести `description` в `requirement_contents` (открытую)
   и/или открыть реквизиты источника (акт/пункт) без verbatim-текста. Решение за схемой.
