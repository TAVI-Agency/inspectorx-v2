# УРОВЕНЬ 0. Общая карта (главная диаграмма)

Шесть слоёв слева направо + один сквозной поперёк:

```
СЛОЙ 0          СЛОЙ 1           СЛОЙ 2            СЛОЙ 3         СЛОЙ 4           СЛОЙ 5
ИСТОЧНИКИ  →    LEGALX      →    КОНВЕЙЕР     →    КУХНЯ     →    INSPECTORX  ←→   АКТИВНЫЕ
(внешний мир)   («сырьё»:        КОНТЕНТА          (HITL-         («витрина»:      ПРОВЕРКИ
                законы)          («завод»:         ревью)         B2B SaaS)        (сервисы:
                └ SudX           карточки)                                         Vision, Doc,
                  (судебная                                                        Translation)
                   практика,
                   схема `court`
                   в БД LegalX) 📋

═══════════════ СКВОЗНОЙ СЛОЙ ИЗМЕНЕНИЙ: diff закона → пересборка карточки → уведомление клиента ═══════════════
```

Логика системы одной фразой: слои 0–4 отвечают на вопрос «что от бизнеса требует
закон», слой 5 — «соответствует ли КОНКРЕТНЫЙ бизнес этим требованиям» (проверка его
фото, документов, сертификатов). Это эволюция из справочника в инспектора.

# СЛОЙ 1. LegalX — платформа законов [RAILWAY worker + SUPABASE + VERCEL фронт]

Конвейер из 7 этапов (эталонная цепочка «источник → структурированный закон»):

## Этап 1.1 — Обнаружение ✅/📋
- LexuzMonitor ✅ — суточный наблюдатель lex.uz: новые акты, новые редакции,
  появление электронных версий вместо сканов.
- RelatedCrawler ✅ — краулинг связанных документов по ссылкам (глубина 2):
  из закона вытягиваются ПКМ, положения, админрегламенты.
- Seed-акты по доменам 📋 — ручной словарь `domains` (фарма, пищёвка, стройка…):
  домен → диапазоны ТН ВЭД/ОКЭД + стартовый список актов.

## Этап 1.2 — Извлечение ✅
- LexuzScraper ✅ — парсинг HTML акта: текст + метаданные (номер, тип, дата, статус, редакция).
- PDF Lab ✅ — конвейер для сканов из 5 агентов:
  Classifier → Preprocessor → Extractor → Structurer → Checker.
  Цифровой PDF и скан идут разными ветками (текст-слой vs VLM-OCR).
- Двухэтапная валидация сканов ✅: скан → предварительная версия → верификация
  по электронной версии, когда она появляется на lex.uz.

## Этап 1.3 — Структура (акт → версия → пункт) 📋 КЛЮЧЕВАЯ СТРОЙКА
- Сейчас: акт хранится монолитным HTML в 3 языках (`act_versions`) ✅.
- Цель: Structurer — разбор на адресуемые юниты `act_units`
  (глава/статья/пункт/подпункт/приложение/строка-перечня) + `act_unit_versions`
  (текст по языкам, content_hash).
- Diff редакций = сравнение хэшей по юнитам → события `unit_changed`.
- Строки перечней из приложений = юниты с полями (ТН ВЭД-код, наименование, условие) —
  фундамент автоматической привязки «акт → товар».
- Стабильность ID юнита между редакциями: матчинг по label → фаззи → LLM-фолбэк.

## Этап 1.4 — Языковой слой ✅→📋
- Сейчас ✅: TranslationPipeline — перевод монолита UZ→RU→EN c юридическим глоссарием
  (`legal_glossary`). Правило: EN всегда из RU, никогда напрямую из UZ.
- Цель 📋: попунктный перевод (юнит = единица перевода, переводим только изменённые юниты).
- Будущее: подключение к слою 5 «Translation» (своя модель или партнёр) — см. слой 5.

## Этап 1.5 — Справочный слой 📋
Синхронизация классификаторов из слоя 0: ТН ВЭД, ИКПУ, ОКЭД, реестр лицензий, БРВ.
Отдельные таблицы с diff-sync. Это словари, на которые ссылается всё остальное.

## Этап 1.6 — Diff и атрибуция изменений ✅
- DiffEngine ✅ — Myers-diff между редакциями + inline redline.
- OmnibusPipeline ✅ — разбор омнибусных указов на отдельные поправки
  (4 агента: Scout → Librarian → Classifier → Applier): какой указ изменил какой пункт.

## Этап 1.7 — Выход слоя
- TelegramBot ✅ — уведомления о новых/изменённых документах с AI-анализом.
- Публичный фронт LegalX ✅ — просмотр документов, сравнение редакций, поиск.
- Админка LegalX ✅ — CRUD, HITL-ревью, импорт документов.
- API/таблицы для слоя 2: акты, юниты, версии, диффы, справочники.

## Этап 1.8 — SudX: судебная практика 📋

Раздел внутри LegalX, а не отдельный продукт и не отдельная база: живёт схемой `court`
в БД LegalX. Причина — один вход в экосистему (Auth привязан к проекту) и джойн
«пункт акта ↔ как его трактовал суд», который между двумя проектами превращается в FDW.
Свой домен куплен, но не одобрен: до одобрения SudX — путь или поддомен внутри LegalX,
отдельного фронта нет.

Три правила с первой миграции — они сохраняют возможность выделить SudX позже
(тогда выделение = `pg_dump -n court` в новый проект):

1. Ссылки на акты — по стабильному внешнему идентификатору (`act_id` + label юнита),
   а не только через FK.
2. Никаких вьюх, функций и триггеров, физически сшивающих схемы. Соединение — только
   на уровне запроса приложения.
3. Отдельный каталог миграций и отдельный набор RLS-политик для `court`.

Триггеры выделения (любой из трёх): корпус решений мешает latency LegalX; у SudX появилась
своя регистрация и биллинг; SudX выделяется как самостоятельный продукт.

# СЛОЙ 2. Конвейер контента («завод»: пункты законов → карточки требований)

## Текущее временное решение 🔶 (research-loop, живёт в repo inspector-x-final)
1. Человек вручную запускает Deep Research по товару/услуге → отчёт (JSON требований).
2. Импортёр: отчёт → черновики требований в БД InspectorX.
3. Гейт качества: авто-проверки (полнота, цитаты, коды) → published или needs_review.
4. Проход 2: доизвлечение точных цитат через LegalX.
Результат на сегодня: 345 требований в проде, 142 через этот конвейер.

## Целевое решение 🔨 (тонкий воркер, перезапись старого Bridge) — контур A
**Факт на ветке `feat/master-plan-1` (мастер-план №1, не в проде):** Build-конвейер
реализован — Cartographer (двухуровневая карта мир→страна, апрув владельцем:
draft→approved, стоп-точка) + Orchestrator из 14 узлов-степов (`importer/build/steps_*.py`:
scope/norm/classify/rule/sanctions/lifecycle/dedup/samples-юрист/cases/translate/load +
ассемблер) + coverage-отчёт (карта vs факт) + публикация по вердиктам + трейсинг
стоимости по ролям (`pipeline.llm_calls`, `build cost`). 552 pytest, синтетический
сквозной пилот на локальном Supabase пройден (published/merge/no_norm). До прод-запуска
не хватает: живого LLM-ключа (раннер — заглушка `NotImplementedError` в `importer/cli.py`)
и данных LegalX по КЗ (гейт D2, задача 43 плана).

Ниже — целевая пятиузловая модель релевантности/классификации из брейншторма; в
реализации её роль частично взял на себя Cartographer (двухуровневая карта), частично —
степы `steps_classify.py`/`steps_rule.py`. Один Python-воркер [RAILWAY], читает `act_units`
из LegalX-БД, пишет в InspectorX-БД (схема `pipeline`). Пять узлов:

1. **Релевантность** — каскад из 3 слоёв, от точного к размытому:
   - A: детерминированный join по кодам (строка перечня содержит ТН ВЭД, покрывающий
     код товара) → авто-publish-grade;
   - B: доменные графы (словарь domains → seed-акты → краулинг) → после валидатора;
   - C: семантический поиск + LLM-фильтр → ТОЛЬКО в ревью, никогда сразу в паблиш.
   Спецслучай КоАО: санкции линкуются к требованию, не к товару.
2. **Классификация** — LLM выбирает ТОЛЬКО из закрытых словарей (тип, категория,
   адресат, этап ЖЦ). Не уверен → REVIEW. Словари правятся в админке.
3. **Extraction** — суть требования + шаги + документы + сроки + санкция;
   legal_verbatim = точная цитата юнита (никогда не перефразируется).
4. **Валидатор** — LLM-судья другого семейства + confidence-скор.
5. **Гейт** — confidence ≥ порога → очередь публикации; ниже → очередь ревью.
   НИ ОДНА карточка не публикуется без человека (см. слой 3).

Отдельный узел 📋: экстрактор «порядок/админрегламент → шаги + документы + сроки»
(источник полей «Как исполнить» — админрегламенты, не законы).

## Гейт качества и трейсинг (контур D) 🔨 — ветка `feat/master-plan-1`
- Golden-набор (`importer/golden/golden_set.yaml`, статус `draft` — ждёт апрува
  владельца пачкой, стоп-точка ②) + харнесс `build eval-golden`: метрики
  retrieval_hit / verifier_agreement (3 суб-метрики) / category_accuracy /
  lifecycle_date_accuracy, near-miss decoy в датасете.
- Трейсинг: каждый LLM-вызов конвейера пишется в `pipeline.llm_calls` (роль,
  токены, стоимость); `build cost --run <id>` собирает markdown-отчёт по ролям.
- Сейчас — только `backend=mock` + эвристический LLM (smoke-проверка проводки
  golden→агент→метрика, НЕ мера качества). Реальный baseline — на живом LegalX
  (гейт D1, задача 42 плана, live-клиент есть — `importer/build/legalx_live.py`,
  приёмка запаркована).

## Наследие старого Bridge (репо ai-compliance-bridge, заморожен с 03.2026)
Забираем: промпты, логику валидатора, структуру узлов. Выбрасываем: Neo4j, Temporal,
Kafka-наследие, свой Postgres, чанкер монолита. Репо — в архив.

# СЛОЙ 3. Кухня контента и админки

## HITL-цикл (правило: без человека ничего не публикуется)
```
AI-генерация → draft → [confidence] → очередь ревью → правка → published
                                            ↑
источник изменился (unit_changed) → flagged_by_change → re_review (авто-возврат)
```
- Приоритет очереди: (1) заявки пользователей «не нашли товар», (2) карточки, задетые
  изменениями законов, (3) горизонтальные требования, (4) новые вертикали.
- Публичная честность: карточка в re_review видна на витрине со значком
  «проверяется обновление».
- Каждое действие логируется (кто/когда/что) — аудит-след.

## Админка InspectorX 📋 (отдельное приложение/раздел)
Очередь ревью и правка карточек · публикация · заявки пользователей · активация
подписок · верификация юристов · премодерация заключений · словари категорий ·
уведомления/колокольчик. Роли: admin / reviewer (юрист) / content-operator.
(Сейчас 🔶 всё это делается руками через service_role и Supabase-дашборд.)

## Консоль конвейера (Bridge-админка) 📋 (отдельная, по решению владельца)
Запуски и статусы прогонов · закрытые словари и домены · пороги confidence ·
просмотр промптов и версий · стоимость/метрики LLM-вызовов. Принцип: всё, что
настраивается — это ДАННЫЕ в таблицах, не код.

# СЛОЙ 4. InspectorX — витрина [VERCEL + SUPABASE Pro] ✅ в проде

## Пользовательский флоу (главный путь)
```
Поиск (товар/услуга/ОКЭД; текст, код, штрих-код, алиасы 3 языков)
  → Страница товара: ПАСПОРТ СООТВЕТСТВИЯ сверху (сколько требований, документов,
    max санкция, что изменилось за 30 дней, индекс сложности, дата проверки)
  → Список требований (строка = требование: заголовок-глагол + тип + адресат +
    ведомство + санкция + статус изменения; категории = фильтры-чипы)
  → Три уровня раскрытия: строка → карточка «что делать» (шаги, сроки, стоимость,
    документы, санкция, FAQ) → юридический слой (точная цитата пункта акта)
  → ПЕЙВОЛЛ: бесплатно — тизер; детали — по подписке. Граница на сервере (RLS),
    активация подписки вручную админом; позже Click/Payme (PayTechUz) 📋
```

## Второй ключевой экран: «Мои товары + лента изменений» 📋
Сводка недели → портфель товаров (счётчики непрочитанного) → лента изменений
(было/стало, важность, дедлайн, «что делать» одной строкой) → настройка дайджеста
(email еженедельно / Telegram мгновенно).

## Вопросы: три ступени ответа 📋
1. AI-ответ (RAG только по опубликованным карточкам, всегда с citation, не уверен →
   честно говорит и предлагает ступень 2) — мгновенно;
2. Юрист команды — 1–2 дня;
3. GR-запрос в госорган — 15–30 дней; официальный ответ обезличенно обогащает FAQ.
Слой доверия на каждом блоке: «AI-черновик» / «Проверено юристом» / «Официальный ответ».

## Верификация юристами-сообществом ✅ (реализовано 29.07.2026)
Онбординг юриста (заявка → ручная верификация) → заключения с вердиктами
(подтверждаю / неточность / устарело / дополнение, премодерация) → бейджи на
требованиях видны всем → голоса «Помогло/Не помогло» → дешборд юриста, очередь
«Ждут проверки», рейтинг топ-10, share-PNG.

## Фичи витрины (принятые)
- Калькулятор стоимости и сроков соответствия 📋 — «выход на экспорт: ~N дней,
  ~M сум», считается из карточек (госпошлины, сроки, документы).
- PDF-отчёт «Паспорт соответствия» 📋 — выгрузка для банка/партнёра.
- Telegram-бот 📋 [RAILWAY, aiogram] — уведомления + вопросы + приём фото для Vision.
- Уведомления: change_events → requirement_change_impacts → user_notifications 🔨 —
  конвейер целиком реализован в ветке `feat/master-plan-1` (impact-mapper + In-house
  lawyer classifier + фан-аут `user_notifications`, `importer/monitoring/impact_mapper.py`),
  не в проде (гейт: живой вебхук LegalX + LLM-ключ classifier'а).
- Календарь дедлайнов (.ics) 🔨 — расширение cron-перехода lifecycle (Miro, контур C):
  личная `.ics`-подписка (`public.calendar_tokens` → `api/calendar/[token].ts`) на
  `effective_from`/`transition_until`/`valid_to`, напоминание за 7 дней. Google
  Calendar OAuth из брифа не реализован — вместо него `.ics`/webcal (решение
  контроллера, проще и без OAuth-интеграции). Код в ветке, не в проде.
- 💡 V2: персонализация по роли, маркетплейс услуг, аналитика портфеля, API/white-label.

# СЛОЙ 5. Активные проверки (проверяем САМОГО клиента против требований)

## 5.1 Vision — проверка фото упаковки/продукта 🔨 (MVP строится сейчас)

Статус: принятая фича продукта, внедряется отдельным треком после запуска (ADR-0002).

Пайплайн проверки:
```
Фото от клиента (веб / Telegram-бот)
  → проверка качества фото (размыто/темно → «переснимите»)
  → детекция зон своей CV-моделью (этикетка, штрих-код, текст маркировки, знаки серт.)
  → OCR текста (латиница + кириллица, uz/ru) + декодирование штрих-кода
  → rule-engine против чек-листа требований маркировки ЭТОГО товара (из карточек слоя 4)
  → Результат: аннотированное фото (обведено ГДЕ проблема) + вердикт по пунктам
    (pass / fail / unreadable / retake) + «что делать» по-русски
```
Цикл улучшения модели: фото клиентов (с согласия) → разметка (VLM-авторазметка +
ручная валидация) → дообучение локально [LOCAL] → выкладка новой версии на [RAILWAY].
Правило владельца (поправка 06.08.2026, `PHOTOCONTROL_INTEGRATION_PLAN.md` §10): **VLM
не производит вердикт и не производит утверждений об отсутствии** (правило двух ключей).
В рантайме VLM даёт гипотезы, которые подтверждает детерминированный чтец (текстовый
слой PDF, OCR, декодер кодов); неподтверждённое становится «подозрением» для человека,
а не результатом. Своя дообучаемая модель (YOLO) остаётся ядром нарезки и единственным
источником рамок зон и знаков.
Деплой: MVP локально → инференс на **Railway CPU**. Ядро (YOLO nano/small + OCR +
декодер штрих-кода + rule-engine) CPU-совместимо, ~2–6 с на снимок — этого хватает
асинхронному воркеру. Modal/RunPod [GPU] — запасной вариант при росте объёма или
требований к latency 📋. Обучение остаётся локальным: Railway GPU не даёт.
Хранение фото: объектное хранилище (R2 / Supabase Storage), не volume Railway 📋.

## 5.2 Doc-checker — проверка документов клиента 📋
```
Клиент грузит свои документы (сертификаты, декларации, разрешения)
  → OCR/extraction полей документа
  → маппинг на список требуемых документов его товара (поле «Документы» карточек!)
  → проверка полей (номера, даты, срок действия, орган выдачи)
  → отчёт готовности: «7/10 документов, не хватает X, в Y ошибка в поле Z»
```
Место: фича кабинета InspectorX (платная), обработка — arq-воркер [RAILWAY].
Зависимость: качество упирается в наполненность поля «Документы» в карточках
(нужен экстрактор админрегламентов из слоя 2).
Сосед 💡: проверка подлинности сертификата по номеру в нацреестрах.

## 5.3 Translation — юридический перевод UZ↔RU (отдельный большой трек) 📋
Этапы трека:
1. Сбор параллельного корпуса — lex.uz как готовый корпус (официальные UZ и RU
   версии одних актов уже в LegalX!) + выравнивание по юнитам.
2. Юридический глоссарий UZ↔RU (частично есть: legal_glossary).
3. Развилка (нужен отдельный deep research): свой файнтюн open-source NMT vs
   API-партнёрство с узбекским NLP-стартапом (например, Tahrirchi) vs
   облачный LLM с глоссарием (текущее решение 🔶).
4. Eval-харнесс: метрики качества + отдельно точность юридических терминов.
5. Сервинг: [RAILWAY] CPU сейчас; [GPU] serverless — запасной вариант, если появится
   своя модель, которой CPU не хватит.
Потребители: слой 1 (перевод актов) и слой 4 (контент витрины).

# СКВОЗНОЙ СЛОЙ ИЗМЕНЕНИЙ (главная нить всей системы, рисовать поперёк всех слоёв)

**Статус (контур C, ветка `feat/master-plan-1`, не в проде):** реализовано целиком.
Webhook приёма `change_events` от LegalX (country-aware, HMAC-секрет в Vault,
`ingest_change_event`) → `monitor process-changes` (точное цитатное совпадение →
флаг + ре-ревью через частичный Build; иначе — эвристический classifier ставит
кандидата в очередь In-house lawyer, ошибки per-item изолированы) → фан-аут
`user_notifications` → `monitor discovery` (свежие `new`-события без impacts →
кандидаты `pipeline.items`) → `requirement_revisions`-история требования. Отдельно —
cron переходов lifecycle (`pg_cron`, 15 мин) уже шлёт уведомления «вступило в силу»/
«закончился переходный период» независимо от webhook. Не хватает для прод-включения:
живого вебхука со стороны LegalX и LLM-ключа classifier'а/In-house lawyer.

```
lex.uz: новая редакция акта
  → [слой 1] LexuzMonitor ловит → новая версия → Structurer → diff юнитов → unit_changed
  → [слой 2] конвейер находит карточки, привязанные к изменённым юнитам
  → [слой 3] карточки → flagged_by_change → re_review (на витрине значок
    «проверяется обновление», карточка НЕ скрывается)
  → [слой 3] ревьюер правит → publish → change_event («было/стало», важность, дедлайн)
  → [слой 4] requirement_change_impacts → user_notifications: у кого этот товар
    в портфеле — бейджи на строках, лента изменений, email/Telegram-дайджест
  → [слой 5] чек-листы Vision/Doc-checker пересобираются из обновлённых карточек
```
Правило: изменение всегда формулируется как изменение ТРЕБОВАНИЯ к товару
пользователя, а не «изменился документ №X». Позитивные изменения помечаются
«в вашу пользу».

# Инфраструктура и эксплуатация (сводка решений 30.07.2026)

- Стиль: модульный монолит в границах существующих репо; сервисы — только по
  триггеру (GPU-сервинг, второй потребитель).
- БД: InspectorX Supabase → Pro + схема `pipeline` для конвейера; LegalX-БД остаётся
  отдельным проектом (базы не сливаем), но с 02.08.2026 — в той же организации, что и
  InspectorX. Pro оплачивается за организацию, поэтому второй проект добавляет ~$10/мес
  компьюта, а не вторые $25. Судебная практика (SudX) — схема `court` внутри LegalX-БД,
  третьего проекта нет.
- Python в Supabase не исполняется: Edge Functions — это рантайм Deno/TypeScript,
  плюс лимиты 256 МБ и 2 с CPU на запрос. Роль базы в запуске работ — только разбудить
  воркер: `pg_cron` для расписаний внутри БД + `pg_net` для HTTP наружу
  (`pg_net` уже используется в `20260727120000_lead_notifications.sql`).
- Бэкапы (уточнение 02.08.2026): Pro = суточные бэкапы, хранение 7 дней. **PITR в Pro не
  входит** — отдельная опция $100/мес за 7 дней глубины. Раньше здесь было написано
  «Pro даёт PITR» — неверно.
- Файлы: Cloudflare R2 (presigned URLs), zero egress.
- Очереди: arq + Redis [RAILWAY] для новых воркеров; processing_jobs в LegalX
  не трогаем, пока работает.
- ML: инференс → Railway CPU; обучение → локальная машина. Modal/RunPod — запасной
  вариант при росте объёма или требований к latency.
- Наблюдаемость: Sentry (все слои) + Better Stack (uptime) + PostHog (продукт) +
  алерты в приватный Telegram-канал. Ставится немедленно.
- CI/CD: GitHub Actions + автодеплой Vercel/Railway. Схема БД тоже деплоится из git:
  GitHub-интеграция Supabase применяет `supabase/migrations/` к проду при мёрже в `main`.
- Платежи: PayTechUz (Click + Payme) 📋, SMS: devsms.uz 📋.
